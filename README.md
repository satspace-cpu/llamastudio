# Llama Studio

**Llama Studio** — программа-менеджер для локальных GGUF-моделей и серверов [llama.cpp](https://github.com/ggml-org/llama.cpp). Одно приложение: запускает и управляет `llama-server`, управляет профилями моделей, GPU, загрузкой моделей с Hugging Face и сборками llama.cpp.

Интерфейс — тёмный, на **русском и английском** языках. Работает в двух формах:

- **Десктоп** (Avalonia) — обычное окно приложения (Windows и Linux);
- **Веб-интерфейс** — встроенный сервер, доступный из любого браузера по сети (по умолчанию `http://<IP-сервера>:8090`). Все страницы веба идентичны страницам десктопа, скриншоты в этой инструкции — веба.

## 1. Возможности

- Запуск, остановка и перезапуск локального сервера llama.cpp.
- Профили: разные модели и рабочие нагрузки в одном приложении.
- Установка **готовых** сборок llama.cpp (CUDA 12/13, Vulkan, CPU, OpenVINO) и **собственных локальных сборок** под ваши видеокарты.
- Распределение модели по одной или нескольким GPU без ручного набора строк устройств.
- Ручное тензорное распределение или автоматическое подбирание llama.cpp.
- Мониторинг: VRAM, RAM (включая выделенную память и кэш), загрузка GPU, мощность, температуры, вентиляторы.
- Поиск по Hugging Face, просмотр файлов репозитория и загрузка GGUF-моделей с паузой и возобновлением.
- Чат через встроенный веб-интерфейс llama-server.
- Веб-интерфейс по сети, логи, системный трей (Windows), автообновление.

## 2. Системные требования

| | Linux | Windows |
|---|---|---|
| Архитектура | x64 (проверено на Debian/Ubuntu) | Windows 10/11 x64 |
| .NET Runtime | **не нужен** (сборка self-contained) | **не нужен** |
| NVIDIA-драйвер | нужен для GPU-сборок | нужен для GPU-сборок |
| CUDA Toolkit | **программа ставит сама** (12.8, драйвер не трогает) | программа ставит сама |
| Для локальных сборок (Linux) | `git`, `cmake`, `gcc`/`g++`, `make`, доступ в интернет (GitHub) | — |
| Память | модель + контекст должны помещаться в VRAM/RAM | то же |

## 3. Установка

### 3.1. Linux

1. Скачайте архив `LlamaStudio-<версия>-linux-x64.tar.gz` со страницы [Releases](https://github.com/satspace-cpu/llamastudio/releases).
2. Распакуйте и запустите:

```bash
tar -xzf LlamaStudio-*-linux-x64.tar.gz
cd LlamaStudio-*-linux-x64
./LlamaStudio
```

Всё, что нужно приложению, находится внутри архива — ставить .NET не нужно.

- Настройки и профили хранятся в `~/.config/LlamaStudio/` (файл `settings.json` и папка `profiles`).
- Веб-интерфейс поднимается сразу после запуска (по умолчанию порт **8090**).

### 3.2. Windows

1. Скачайте `LlamaStudio.exe` со страницы [Releases](https://github.com/satspace-cpu/llamastudio/releases).
2. Запустите. exe самодостаточный, .NET не нужен.

### 3.3. Первый запуск

При открытии вы видите главное окно (или вкладку «Главная» в вебе):

![Главная](screenshots/web-01-home.png)

Карточки сверху: **Сервер** (Running/Stopped + кнопка запуска/остановки), **Модели** (сколько GGUF найдено в папке моделей), **Профили** (активный профиль и список), **llama.cpp** (выбранная сборка и кнопка проверки обновлений), **Llama Studio** (версия приложения). Ниже — карточка **активного профиля** (модель, mmproj, черновик, контекст, температура, слои GPU, включённые режимы: MTP, Flash Attention, кэш промпта, непрерывный батч) и **живый блок «Использование GPU»** (RAM и все GPU).

Слева — навигация: Главная, Чат, Модели, Мониторинг, Релизы llama.cpp, Сервер, Логи, Настройки, Обсуждение и поддержка. Внизу — кнопки управления сервером.

## 4. Первые 5 минут

1. **Настройки** → укажите папку с моделями (или оставьте пустую — скачаете через Hugging Face).
2. **Модели** → скачайте модель (раздел 6) или положите GGUF в папку и нажмите «Обновить список».
3. **Релизы llama.cpp** → «Проверить обновления» → выберите сборку под вашу карту → «Установить» (раздел 5; локальная сборка идёт 30–40 минут).
4. **Сервер** → «Создать профиль», выберите модель и установленную сборку llama.cpp → «Запустить сервер».
5. **Мониторинг** → убедитесь, что модель грузится в память, и нажмите «Измерить скорость».

## 5. llama.cpp: установка и сборки

![Релизы llama.cpp](screenshots/web-04-releases.png)

Страница разделена на две панели. **Слева** — доступные релизы (с GitHub llama.cpp), **справа** — установленные сборки (в «Папке с серверами llama.cpp», путь задаётся вверху страницы).

### 5.1. Что означают карточки в списке релизов

Каждая карточка — один вариант сборки для одного релиза (тега):

- **local build** — «под ваши карты»: сборка будет скомпилирована **только под архитектуру обнаруженных GPU** (например, `sm80`). Маленькая, быстрая, именно её программа рекомендует, если видит NVIDIA-карты (бейдж «Build CUDA 12 + RPC for NVIDIA GPUs detected on this computer»).
- **universal** — «полная сборка»: компилируется **под все архитектуры NVIDIA сразу**. Работает на любой карте, но больше и компилируется дольше.
- **CUDA 12 / CUDA 13** — ветка CUDA. Для CUDA 12 программа автоматически установит CUDA Toolkit 12.8, если его ещё нет (NVIDIA-драйвер при этом **не меняется**).
- **Vulkan, CPU, OpenVINO** — сборки под другие бэкенды.
- Галочка **NCCL (multi-GPU)** — включить NCCL: для нескольких GPU одна модель распределяется быстрее и эффективнее (только CUDA, несколько карт).

Кнопка **«Установлено»** (серая, неактивная) означает, что именно этот вариант уже установлен. Серая же выглядит и любая другая неактивная кнопка — активные кнопки всегда яркие.

### 5.2. Что делает программа при установке локальной сборки (Linux)

1. Клонирует исходники llama.cpp с GitHub на нужное состояние (тег релиза) в служебную папку `.llama-studio-source/<версия>` (≈28 МБ; при медленном интернете этот этап займёт заметно больше всего времени — клон виден в «Логах»).
2. При отсутствии ставит **CUDA Toolkit 12.8** (≈3 ГБ, только для сборки; драйвер NVIDIA не затрагивается).
3. Собирает проект из исходников (cmake + компилятор) под вашу архитектуру: для одной карты — `sm80` (и т.п.), для нескольких — те же архитектуры + **NCCL**. Это и есть самая долгая часть: **30–40 минут** на типичном сервере. Во время сборки кнопка установки неактивна, прогресс виден в полосе над карточками.
4. Проверяет результат: запускает собранный `llama-server --version` и сверяет commit со встроенным в тег релиза. При несовпадении установка считается несостоявшейся.
5. Кладёт результат в папку установок: `<папка с серверами>/<версия>-cuda12x-local-sm80-nccl/`.

**Что попадает в папку сборки** (пример — b10819): исполняемый `llama-server`, все утилиты (`llama-cli`, `llama-bench`, `llama-quantize`, `llama-gguf`, `llama-server` и десятки других, включая тесты), библиотеки `libggml-*`, `libllama-*`, `libmtmd*` и **NCCL** (`libnccl.so`), а также CUDA-библиотеки, против которых собиралось (`libcudart.so.12`, `libcublas*` и т.д.). Сборка самодостаточная: после установки дополнительные компоненты не нужны.

> После установки перезагрузите страницу (или нажмите «Обновить» в панели «Установленные версии») — карточка станет серой «Установлено».

### 5.3. Установленные версии

Правая панель показывает все сборки в папке:

- **Использовать** — назначить эту сборку активным выбором (она появится в профиле, «Версия llama.cpp»).
- **Удалить** — удалить папку сборки (активную удалить нельзя).
- Бейдж **Активна** — сборка, которую сейчас использует активный профиль.
- Под каждой — commit и строка версии llama.cpp.

### 5.4. Экспериментальные сборки

Вкладка «Экспериментальные» позволяет указать **любой** GitHub-репозиторий (например, fork llama.cpp с новыми фичами) и собрать его тем же способом. Для экспериментов — не для повседневной работы.

### 5.5. Строка версии llama.cpp

Свежие релизы llama.cpp имеют вид `version: 0.4.0-dev (build 1, commit 6a1a922)`. Это новая схема нумерации самого llama.cpp (переход на version-теги): «build 1» — это **не** ошибка и не номер сборки Llama Studio. Llama Studio сверяет по **commit**, поэтому установка и активация работают корректно.

## 6. Модели: локальные и Hugging Face

![Модели](screenshots/web-02-models.png)

### 6.1. Локальные GGUF

Вверху страницы — поиск и список моделей из папки, указанной в настройках. Для каждой модели: имя, квантизация (Q4_K_M, BF16…), размер, путь и кнопки:

- **Модель сервера** — назначить файл основной моделью активного профиля;
- **Использовать mmproj** — назначить файл проектором зрения (mmproj) для мультимодальных моделей.

Для **разделённых на части** моделей (shards) файл называется как `00001-of-00002.gguf`, `00002-of-00002.gguf` — это **одна** модель, разрезанная на файлы. В профиле указывается первый файл; остальные подхватываются автоматически по именованию.

### 6.2. Hugging Face

Верхняя панель «HuggingFace Download»:

1. **Токен** (необязательно) — для приватных репозиториев: получите токен на huggingface.co → Settings → Access tokens, вставьте и нажмите «Сохранить токен». Токен хранится локально.
2. **Поиск** — введите название (например, `Qwen3.8` или `Llama-3.1-8B`), выберите репозиторий из результатов.
3. **Файлы** — программа получает список файлов репозитория; нужны галочки на GGUF-файлах, которые вы скачиваете. Для shard-модели отметьте **все** части `00001-of-…`, `00002-of-…` и (если есть) подходящий `mmproj`. Для MTP-моделей — также draft-файл `mtp-*.gguf` (он станет «Черновиком» в профиле).
4. **Скачать** — загрузка в папку моделей.

Загрузка работает на **частичных файлах**: пауза, перезапуск программы или выключение компьютера не обнуляют прогресс — скачивание продолжается с места остановки. Кнопки: Пауза / Отмена. Следите за свободным местом: размер каждого файла виден в списке.

## 7. Профили

![Сервер](screenshots/web-05-server.png)

**Профиль** — это именованный комплект настроек «модель + параметры + сборка llama.cpp». Под каждую модель/нагрузку свой профиль: переключение профиля = переключение всего рабочего места.

Кнопки над списком: **Создать профиль**, **Переименовать**, **Удалить**, **Сделать дефолтным** (профиль, который открывается при запуске), **Копировать** (дубликат текущего), **Очистить без моделей** (сбросить параметры, оставив модель).

### 7.1. Вкладка «Модель»

- **Основная модель** — путь к GGUF (или назначьте кнопками на странице «Модели»).
- **Зрение (mmproj)** — путь к mmproj для мультимодальных моделей; можно не указывать.
- **Черновик (MTP)** — draft-модель для спекулятивного декодирования (файл `mtp-*.gguf`).
- **Версия llama.cpp** — какая установленная сборка запускает сервер.

### 7.2. Вкладка «GPU»

- **Слои GPU** — сколько слоёв модели offload-ить в GPU (`all` — все, которые влезут; число — точное).
- **Режим распределения** — `layer` (слои идут по одной карте за другой) или `tensor` (каждый слой разрезается по картам — только для нескольких GPU).
- **Выбранные GPU** — чекбоксы обнаруженных карт; отмеченные участвуют в offload.
- **Основной GPU** — какая карта «главная» (актуально для одной карты или режима layer).
- Для нескольких GPU — **ручное распределение в процентах** (`--tensor-split`): например 50/50 или 60/40; кнопки ±1% и ±5% для точной настройки. Либо **Авто** — пусть llama.cpp сам подберёт распределение под доступную память.
- **Flash Attention, KV offload** — ускорения/оптимизации памяти (включаются флагами сервера).

> `--tensor-split` — это распределение **тензоров модели** по картам, а не «проценты нагрузки». При авто-режиме программа не пишет split — llama.cpp сам решает по памяти.

### 7.3. Вкладки «Контекст» и «Сэмплинг»

- **Контекст**: `Context size` (окно контекста, например 32768), `Batch size` / `UBatch size` (размеры батчей обработки промпта), `Threads` (потоки CPU).
- **Сэмплинг**: `Temperature`, `Top-K`, `Top-P`, `Min-P`, `Typical-P`, `Repeat penalty` и другие параметры генерации. Оставленные «по умолчанию» значения не пишутся в команду.

### 7.4. Вкладка «KV Кэш»

- `Cache type K/V` — тип квантизации KV-кэша (F16/Q8_0/Q4_0…) — экономит VRAM.
- `Cache RAM` — лимит RAM-кэша (сколько гигабайт системы отдавать под кэш); видно в мониторинге как «кэш: до N GB».
- `Cache reuse`, `Cont. batching`, `Context shift` — повторное использование кэша, непрерывное батчинг нескольких запросов, сдвиг контекста при переполнении.

### 7.5. Вкладки «MTP и Спекулятивное», «Rope/YARN»

- **MTP и Спекулятивное**: тип спекулятивного декодирования (`draft-mtp` — встроенные MTP-слои модели), лимит шагов. Ускоряет генерацию, если у модели есть MTP-слои (бейдж «MTP» на главной).
- **Rope/YARN**: масштабирование позиционных кодировок для длинного контекста (YARN-факторы) — только если вы расширяете контекст за пределами нативного.

### 7.6. Вкладка «Сервер»

Параметры самого `llama-server`: адрес и порт (по умолчанию `0.0.0.0:8080`), слоты, метрики, **встроенный веб-интерфейс сервера** (чат), API-ключ (необязательно), логирование.

### 7.7. Вкладка «Пользовательские аргументы» — что это

Поле **Custom Arguments** — любые дополнительные аргументы, которые приложение добавит к команде запуска `llama-server` **после** всех остальных. Это «ручное управление» для случаев, когда штатных настроек не хватило. Примеры:

```
--prio 10                 # приоритет CPU-процесса
--no-mmap                 # не использовать mmap для модели
--cache-type-k q8_0       # переопределить тип кэша (если поле в KV-вкладке не подошло)
--jinja                   # шаблонизация чат-шаблонов
```

Правила: аргумент пишется как в терминале (флаг и значение), несколько аргументов — через пробел или перевод строки; конфликтующий со штатным флаг **перекрывает** его (llama.cpp принимает последнее). Перед запуском всегда смотрите **команду запуска** ниже — она показывает точную итоговую команду.

### 7.8. Команда запуска

Блок «Профиль и команда запуска» показывает **точную** команду, которой стартует сервер. Кнопки:

- **Обновить команду** — пересобрать превью из текущих полей;
- **Копировать команду** — в буфер обмена;
- **Экспорт .bat** — сохранить запуск как Windows-скрипт (удобно запустить без Llama Studio);
- **Импорт .bat** — загрузить готовый .bat в профиль.

### 7.9. Вкладка «Удалённый RPC»

Параметры подключения к GPU другой машины (раздел 12).

## 8. Сервер: запуск и управление

На странице «Сервер» (и на «Главной»):

- **Запустить / Остановить / Перезапустить** — управление процессом `llama-server`.
- Состояние видно вверху: `Running`/`Stopped` + VRAM, RAM, токены/с.
- При **смене профиля**, если сервер запущен, приложение автоматически его перезапускает с новым профилем (это нормальное поведение, не ошибка).
- Лог загрузки модели и ошибки — на странице «Логи» (раздел 13).

## 9. Мониторинг

![Мониторинг](screenshots/web-03-monitoring.png)

### 9.1. Карточки GPU

Для **каждой** GPU (локальной и удалённой через RPC) — своя карточка:

- **VRAM** — занято/всего (ГБ);
- **Загрузка GPU** — утилизация в %;
- **Мощность GPU** — текущая мощность и лимит (W);
- **Температура GPU / памяти** — °C;
- **Вентилятор** — % (если карта отчитывается).

Вверху — сводные карточки: **Все GPU** (суммарный VRAM, суммарная загрузка, суммарная мощность) и **Мощность всех GPU** (сумма / сумма лимитов).

### 9.2. RAM

Карточка **RAM** показывает систему:

- **занято / всего** — обычное использование ОЗУ;
- **выделено: N GB** — память, выделенная ОС под процесс llama-server (включая модель, если она в RAM/mmap);
- **кэш: до N GB** — лимит RAM-кэша из профиля (KV offload).

## 10. Измерение скорости

Вверху «Мониторинга» (и на «Сервере») — блок **Скорость генерации** с кнопкой **Измерить скорость**:

- **Токены генерации** (токенов/с) — скорость «потоковой» генерации: по одному токену за раз. Это то, что вы видите при переписке с моделью.
- **Обработка промпта** (промпт токенов/с) — скорость обработки входного текста батчами. Всегда заметно выше, чем генерация: модель обрабатывает много токенов параллельно.

Кнопка запускает встроенный бенчмарк (несколько секунд — пара минут, зависит от модели): приложение посылает тестовый промпт и меряет обе скорости. Во время замера генерация в чате будет тормозить — это нормально.

## 12. Удалённый RPC (GPU другой машины)

![RPC](screenshots/web-07-rpc.png)

**RPC** — это способ использовать GPU **другой машины** как продолжение вашей: llama.cpp умеет работать с `ggml-rpc-server`, который запускается на удалённой машине и отдаёт её GPU по сети.

Вкладка «Удалённый RPC» (в вебе — отдельная страница, в профиле — вкладка):

- **Rpc endpoint** — адрес удалённого RPC-сервера (например `tcp://192.168.1.50:50052`);
- **SSH-логин/пароль** (необязательно) — Llama Studio по SSH сама поднимет/остановит `ggml-rpc-server` на удалённой машине; без SSH RPC-сервер нужно запускать вручную;
- **Сохранять пароль** — разрешить хранить пароль локально;
- **RPC-кэш** — кэшировать уже загруженные на удалённую машину веса между запусками;
- **Телеметрия** — передавать данные GPU удалённой карты в мониторинг (она появится в списке GPU с бейджем «RPC»).

В мониторинге удалённые карты отображаются как обычные, с пометкой **RPC**.

## 13. Логи

![Логи](screenshots/web-08-logs.png)

Журнал событий приложения и llama-server: старт сервера, загрузка модели, выбор устройств, тайминги промпта и генерации, ошибки. Это **первое место**, куда смотреть, когда:

- модель не влезает в память (ищите `failed to allocate ... kv cache` — не хватает места под KV-кэш: уменьшите контекст/KV-кэш или добавьте GPU);
- сервер не стартует (ошибка аргумента, неверная сборка);
- GPU «не тот» (в логе видно, какие устройства реально выбраны).

## 15. Множество GPU: краткий план

1. Установите нужную сборку llama.cpp (раздел 5): для NVIDIA с несколькими картами — **local CUDA + NCCL**.
2. Откройте **Сервер → вкладка GPU**, дождитесь обнаружения устройств.
3. Отметьте чекбоксами карты, которые участвуют.
4. Режим `tensor` + распределение (ручное в % или авто).
5. Проверьте превью команды: `--tensor-split` и список устройств должны совпадать с намерением.
6. Перезапустите сервер и посмотрите обе карточки GPU в мониторинге.

Память — не только модель: контекст, KV-кэш, батчи, mmproj и черновик тоже едят VRAM. Если суммарно «хватает», а модель всё равно не влезает — см. FAQ.

## 16. FAQ

**Кнопка «Установить» не меняется. Что происходит?**
Локальная сборка идёт 30–40 минут (плюс скачивание исходников и CUDA Toolkit при первом разе). Кнопка неактивна всё это время — это нормально. Прогресс — в полосе над карточками. После завершения обновите страницу: кнопка станет серой «Установлено».

**Почему версия llama.cpp «0.4.0-dev, build 1»?**
Это новая схема нумерации в самом llama.cpp. Llama Studio проверяет сборки по **commit**, а не по номеру build — установка корректна.

**Модель не влезает в VRAM, хотя «места вроде хватает»?**
В VRAM живут не только веса: контекст + KV-кэш + батчи + mmproj + черновик + служебные буферы. Уменьшите `Context size`, включите квантованный KV-кэш (Q8_0/Q4_0), уберите/уменьшите черновик или добавьте вторую карту.

**Что выбрать: local или universal?**
Для вашей конкретной карты — **local** (меньше, быстрее, скомпилирована точно под вашу архитектуру). **Universal** — если карты разные/меняются и одна сборка должна работать везде (большая, компилируется дольше).

**Авто-распределение или ручное?**
Начинайте с **авто** — llama.cpp подберёт split под реальную доступную память (особенно если карты разные). Ручное — когда нашли стабильное распределение и хотите его зафиксировать.

**Почему промпт быстрее генерации?**
Это две разные операции: промпт обрабатывается батчами (параллельно), генерация — по одному токену за раз (авто регрессивно). Разница в десятки раз — норма.

**Где хранятся данные?**
Настройки и профили — `~/.config/LlamaStudio/` (Linux) или `%APPDATA%` (Windows). Модели и сборки llama.cpp — в папках, указанных в настройках. Ничего не пишется в облако, кроме проверок обновлений и (по желанию) поиска/скачивания с Hugging Face.

**Как обновить само Llama Studio?**
Linux: скачайте новый архив с [Releases](https://github.com/satspace-cpu/llamastudio/releases), распакуйте в новую папку и запустите. Настройки и профили останутся — они лежат отдельно от программы.
